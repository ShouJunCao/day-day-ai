6.7 上下文管理（压缩、过滤、Lost in the Middle）

模块六：RAG 系统构建 预计学习：50 分钟

学习目标

  • 理解上下文管理在 RAG 系统中的重要性
  • 掌握上下文压缩、过滤、Lost in the Middle 处理三种技术
  • 学会构建完整的上下文管理流水线
  • 了解上下文长度限制对 RAG 系统的影响

一、为什么需要上下文管理？

在 RAG 系统中，检索模块返回的相关文档会被拼接到 Prompt 中作为上下文。随着检索文档数量的增加，上下文长度也会不断增长。然而，LLM 对上下文的处理能力并非线性的。

上下文管理面临三个核心挑战。第一是 Token 限制：每个模型都有最大上下文长度限制，超出限制的文档会被截断。第二是噪声干扰：检索结果中可能包含不相关或低相关的文档，这些噪声会降低回答质量。第三是 Lost in the Middle：研究表明，当上下文过长时，LLM 容易忽略中间部分的信息，只关注开头和结尾的内容。

这些问题共同决定了 RAG 系统的最终效果。即使检索模块能够召回高相关文档，如果上下文管理不当，这些信息仍然无法被 LLM 有效利用。因此，上下文管理是 RAG 系统中不可或缺的一环，其重要性不亚于检索和重排序本身。

在实际项目中，我们经常会遇到这样的问题：检索结果明明包含了正确答案，但 LLM 生成的回答却偏离了预期。这种情况很大程度上是由上下文管理不当造成的。通过有效的过滤、压缩和重排序，可以显著提升 LLM 对上下文的利用率，进而改善最终的问答质量。

二、上下文压缩

上下文压缩的核心思想是在不丢失关键信息的前提下，减少上下文的 Token 数量。通过压缩，可以在有限的 Token 预算内容纳更多的有效信息。

压缩的必要性在于：检索结果中往往包含大量冗余信息。比如多个文档可能描述了相同的事实，或者某些文档中只有个别句子与查询相关。如果不进行压缩直接拼接所有文档，不仅会浪费 Token 预算，还可能引入不必要的噪声。

2.1 压缩策略

策略原理优点缺点
句子级压缩 按句子分割，保留重要句子 实现简单，速度快 可能丢失上下文关联
LLMLingua 使用语言模型 perplexity 选择信息量高的内容 语义保持好 需要额外模型
LLM 摘要 让 LLM 对长文档生成摘要 最灵活 成本高，有幻觉风险
关键词保留 保留包含查询关键词的句子 极快，无需模型 可能遗漏语义相关信息

class ContextCompressor:
    """
    上下文压缩器：使用语言模型 perplexity 或启发式方法压缩上下文。

    原理：
    1. 计算每个文档/句子的信息量
    2. 保留高信息量内容，删除冗余部分
    3. 在保持语义完整性的同时减少 Token 数
    """

    def __init__(self, compression_ratio: float = 0.5):
        """
        初始化压缩器。

        参数：
        - compression_ratio (float): 压缩比例（0.5 表示保留 50%）
        """
        self.compression_ratio = compression_ratio

    def compress(self, context: Context) -> Context:
        """压缩上下文"""
        compressed_docs = []
        for doc in context.documents:
            sentences = self._split_sentences(doc)
            important = self._select_important_sentences(sentences, context.query)
            compressed_docs.append(" ".join(important))
        return Context(documents=compressed_docs, query=context.query)

    def _select_important_sentences(self, sentences, query):
        """选择重要句子：基于与查询的关键词重叠度"""
        query_words = set(query.replace(" ", ""))
        scored = []
        for sent in sentences:
            sent_words = set(sent.replace(" ", ""))
            overlap = len(query_words & sent_words) / max(len(query_words), 1)
            scored.append((sent, overlap))

        scored.sort(key=lambda x: x[1], reverse=True)
        keep_count = max(1, int(len(sentences) * self.compression_ratio))
        selected = [s for s, _ in scored[:keep_count]]
        return [s for s in sentences if s in selected]

三、上下文过滤

上下文过滤是在将检索结果送入 Prompt 之前，基于相关性分数剔除低价值文档的过程。过滤的核心目标是去伪存真，只保留真正对回答有帮助的文档。

过滤策略通常基于重排序阶段产生的相关性分数。设定一个阈值，只保留分数高于阈值的文档。阈值的选择需要根据实际场景调整：阈值过高可能导致信息不足，阈值过低可能引入噪声。一般来说，0.6 是一个不错的起点，但需要根据具体任务进行评估和调整。

class ContextFilter:
    """
    上下文过滤器：基于相关性阈值过滤检索结果。

    原理：
    1. 计算每个文档与查询的相关性分数
    2. 过滤掉低于阈值的文档
    3. 只保留高相关性文档进入 Prompt
    """

    def __init__(self, threshold: float = 0.6):
        """
        初始化过滤器。

        参数：
        - threshold (float): 相关性阈值
        """
        self.threshold = threshold

    def filter(self, context: Context, scores: List[float]) -> Context:
        """过滤上下文"""
        filtered_docs = []
        for doc, score in zip(context.documents, scores):
            if score >= self.threshold:
                filtered_docs.append(doc)

        return Context(
            documents=filtered_docs,
            query=context.query,
            max_tokens=context.max_tokens,
        )

四、Lost in the Middle 问题

Lost in the Middle 是一个被多项研究证实的现象：当 LLM 处理长上下文时，位于中间部分的信息被忽略的概率显著高于开头和结尾部分。这种现象对 RAG 系统的影响尤为严重，因为检索结果通常按相关性排序，如果简单地将所有文档拼接在一起，中间的相关文档可能被 LLM 忽略。

4.1 现象解释

Liu 等人在 2023 年的论文中系统地研究了这个问题。他们发现，当上下文长度超过一定阈值后，LLM 对中间部分信息的利用率会急剧下降，形成一个 U 形的信息利用曲线。

4.2 解决策略

策略原理效果成本
文档重排序 将最相关文档放在开头和结尾 显著提升 低（仅排序）
分段摘要 对中间部分生成摘要再拼接 中等提升 中（LLM 调用）
分块处理 将长上下文拆分为多个块分别处理 较好 高（多次推理）

4.3 代码实现

class LostInTheMiddleHandler:
    """
    Lost in the Middle 处理器：解决长上下文中部信息丢失问题。

    策略：
    - reorder: 最相关文档放首尾
    - summarize: 分段摘要
    - chunk: 分块处理
    """

    def _reorder(self, context, scores):
        """重新排序：将最相关的文档放在开头和结尾"""
        paired = list(zip(context.documents, scores))
        paired.sort(key=lambda x: x[1], reverse=True)

        reordered_docs = []
        left, right = 0, len(paired) - 1
        while left <= right:
            if left == right:
                reordered_docs.append(paired[left][0])
            else:
                reordered_docs.append(paired[left][0])
                reordered_docs.append(paired[right][0])
            left += 1
            right -= 1

        return Context(documents=reordered_docs, query=context.query)

五、完整上下文管理流水线

在实际应用中，这三种技术通常是组合使用的。一个完整的上下文管理流水线包含三个步骤：先过滤去除低相关性文档，再压缩保留关键信息，最后重排序解决 Lost in the Middle 问题。

5.1 代码实现

class ContextManager:
    """
    统一上下文管理调度器：组合压缩、过滤、Lost in the Middle 处理。
    """

    def __init__(self, compress=True, filter=True, handle_litm=True):
        self.compressor = ContextCompressor() if compress else None
        self.filter = ContextFilter() if filter else None
        self.litm_handler = LostInTheMiddleHandler() if handle_litm else None

    def process(self, context, scores=None):
        """处理上下文：过滤 → 压缩 → 重排序"""
        if scores is None:
            scores = [0.5] * len(context.documents)

        if self.filter:
            context = self.filter.filter(context, scores)
        if self.compressor:
            context = self.compressor.compress(context)
        if self.litm_handler:
            context = self.litm_handler.handle(context, scores)

        return context

六、最佳实践

基于实际项目经验，以下是上下文管理的关键最佳实践：

  • 先过滤再压缩：先剔除低相关性文档，再压缩剩余文档，效率更高。如果先压缩再过滤，可能会浪费计算资源在即将被丢弃的文档上
  • 阈值动态调整：根据查询类型和检索结果分布动态调整过滤阈值。对于专业领域查询，可以适当降低阈值以捕获更多相关文档
  • 重排序必须做：无论上下文多短，都应该将最相关文档放在开头，这是解决 Lost in the Middle 问题最直接有效的方法
  • 监控 Token 使用：建立上下文长度监控，及时告警超限情况。设置合理的上下文长度上限，避免 Token 溢出
  • 评估效果：使用 RAGAS 等框架评估上下文管理对最终回答质量的影响。通过离线评估集量化不同配置的效果差异
⚠️ 过度压缩的风险

过度压缩可能导致关键信息丢失。建议设置压缩上限（如保留率不低于 30%），并通过离线评估集验证压缩后对回答质量的影响。如果发现压缩导致回答质量下降，应该降低压缩比例或更换压缩策略。

七、小结

上下文管理是 RAG 系统中确保检索信息被有效利用的关键环节。上下文压缩通过减少 Token 数量提高信息密度，上下文过滤通过剔除低相关性文档去除噪声，Lost in the Middle 处理通过重排序文档确保关键信息不被忽略。

在实际项目中，建议构建完整的上下文管理流水线：先过滤、再压缩、最后重排序。这种组合方式能够在有限的 Token 预算内最大化有效信息量，同时确保 LLM 能够充分利用这些信息生成高质量的回答。
