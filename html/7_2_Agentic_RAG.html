7.2 Agentic RAG（Agent 自主检索路由）

模块七：高级 RAG 技术 预计学习：50 分钟

学习目标

  • 理解传统 RAG 的固定流程局限性
  • 掌握 ReAct Agent 范式在 RAG 中的应用
  • 学会构建路由 Agent 实现智能策略选择
  • 了解 Agentic RAG 与传统 RAG 的优劣对比

一、为什么需要 Agentic RAG？

传统 RAG 系统遵循固定的流程：用户提问 → 向量检索 → 重排序 → Prompt 构建 → LLM 生成。这种流程对于简单问题效果良好，但面对复杂问题时存在明显局限。

主要问题包括：第一，流程僵化。无论问题简单还是复杂，都执行相同的步骤，无法根据问题难度动态调整。第二，缺乏推理能力。传统 RAG 无法进行多步推理，当答案需要综合多个信息源时，效果大打折扣。第三，无法自主决策。系统不能根据检索结果的质量决定是否需要补充检索或更换策略。第四，缺乏自我验证能力。即使检索结果质量不佳，传统 RAG 仍然会将结果交给 LLM 生成回答，可能导致错误或低质量的输出。

Agentic RAG 通过将 Agent 技术引入 RAG 系统，解决了这些问题。Agent 具备自主决策能力，能够根据问题的类型和复杂度，动态选择最合适的检索策略和工具组合。这种转变不仅仅是技术上的升级，更是思维方式的根本变化：从"系统按照预设流程执行"转变为"系统自主思考并决定最佳行动方案"。

从技术演进来看，Agentic RAG 代表了 RAG 系统从"被动执行"向"主动决策"的转变。它不再是一个固定的流水线，而是一个能够思考、决策和执行的智能系统。这种能力使得 Agentic RAG 能够处理更复杂、更多样化的用户请求，为 RAG 技术的应用场景开辟了新的可能性。

二、ReAct Agent 范式

ReAct（Reasoning + Acting）是目前最主流的 Agent 范式。它将推理和行动结合起来，让 Agent 能够在执行任务的过程中不断思考、观察和调整。

ReAct 的核心循环包含四个步骤：思考（Thought）决定下一步行动，执行（Action）调用工具获取信息，观察（Observation）分析工具返回的结果，然后循环执行直到得出最终答案。这种范式最早由 Yao 等人在 2022 年提出，后来成为构建智能 Agent 的标准方法。

ReAct 的优势在于：每一步都有明确的推理过程，Agent 的行为是可解释的；同时，通过观察结果来调整后续行动，使系统具备一定的自适应能力。在 RAG 场景中，ReAct Agent 可以根据检索结果的质量决定是否需要补充检索、更换策略，或者直接生成答案。

与传统 RAG 的固定流程不同，ReAct Agent 的每一步都是动态决定的。这意味着对于简单问题，Agent 可能只需要一步检索就能回答；对于复杂问题，Agent 可以执行多步推理，综合多个信息源。这种灵活性是 Agentic RAG 的核心价值所在。

2.1 代码实现

07_advanced_rag/02_agentic_rag/agentic_rag.py
class ReActAgent:
    """
    ReAct Agent：基于 ReAct 范式的智能代理。

    原理：
    1. Thought：思考下一步应该做什么
    2. Action：执行具体动作（如检索、计算、查询）
    3. Observation：观察动作的结果
    4. 循环执行直到得出最终答案
    """

    def __init__(self, tools: List[Callable], max_steps: int = 5):
        self.tools = {tool.__name__: tool for tool in tools}
        self.max_steps = max_steps
        self.steps = []

    def execute(self, question: str) -> AgentResult:
        """执行 Agent 推理流程"""
        self.steps = []
        route_taken = []

        for step_num in range(1, self.max_steps + 1):
            # 1. Thought：决定下一步行动
            thought = self._decide_next_step(question, step_num)

            # 2. Action：选择并执行工具
            action_name, action_input = self._select_action(thought)
            action = AgentAction(
                action_name=action_name,
                action_input=action_input,
                thought=thought,
            )

            # 3. Observation：执行工具并观察结果
            if action_name in self.tools:
                result = self.tools[action_name](action_input)
                action.action_result = str(result)

            step = AgentStep(step_number=step_num, action=action,
                           observation=str(result))
            self.steps.append(step)
            route_taken.append(action_name)

            # 4. 判断是否得出答案
            if self._is_final_answer(action_name, result):
                break

        return AgentResult(answer=..., steps=self.steps,
                          confidence=..., route_taken=route_taken)

三、路由 Agent

路由 Agent 是 Agentic RAG 的另一种重要模式。它根据用户问题的类型，自动选择最合适的检索策略。

与 ReAct Agent 不同，路由 Agent 不需要多步推理。它的核心能力是"识别问题类型"，然后"选择合适的工具"。这种模式适合那些需要多种检索策略但问题类型相对明确的场景。

3.1 代码实现

class RoutingAgent:
    """
    路由 Agent：根据问题类型自动选择最佳检索策略。

    支持的策略：
    - vector_search: 向量检索（默认）
    - keyword_search: 关键词检索
    - graph_search: 图谱检索
    - hybrid_search: 混合检索
    """

    STRATEGIES = {
        "vector_search": "向量检索",
        "keyword_search": "关键词检索",
        "graph_search": "图谱检索",
        "hybrid_search": "混合检索",
    }

    def route(self, question: str) -> str:
        """根据问题类型选择最佳策略"""
        if any(kw in question for kw in ["什么", "谁", "哪里"]):
            return "vector_search"
        elif any(kw in question for kw in ["比较", "区别", "对比"]):
            return "hybrid_search"
        elif any(kw in question for kw in ["关系", "关联", "联系"]):
            return "graph_search"
        else:
            return "keyword_search"

3.2 路由规则扩展

在实际项目中，路由规则可以根据业务需求进行扩展。除了基于关键词的简单规则，还可以使用分类模型来实现更精准的路由。例如，训练一个文本分类模型，将用户问题分为"事实型"、"比较型"、"推理型"和"操作型"四类，然后为每类问题选择最合适的检索策略。

基于模型的路由相比基于规则的路由有显著优势：它能够理解问题的语义，而不仅仅是匹配关键词。这意味着即使用户使用不同的表达方式来询问相同的问题，路由系统也能正确分类。例如，"X 和 Y 有什么不同"和"比较一下 X 与 Y"虽然关键词不同，但都属于比较型问题，应该使用混合检索策略。

此外，路由系统还可以考虑上下文信息。比如，根据用户的历史查询记录、当前会话状态和可用的数据源来动态调整路由决策。这种上下文感知的路由能够提供更精准的检索策略选择，进一步提升问答质量。

四、Agentic RAG vs 传统 RAG 全面对比

Agentic RAG 与传统 RAG 的核心差异在于决策方式。传统 RAG 遵循预设的固定流程，每一步都是确定的；而 Agentic RAG 的 Agent 能够根据当前状态动态决定下一步行动。这种差异使得 Agentic RAG 在处理复杂问题时具有显著优势，但也带来了更高的复杂度和成本。

工具使用 单一检索 多工具组合

可解释性 中等 高（推理链可见）

五、Agentic RAG 的适用场景

Agentic RAG 并非在所有场景下都优于传统 RAG。它的优势主要体现在需要自主决策和多步推理的场景中。

5.1 工具定义示例

在 Agentic RAG 中，工具是 Agent 的"手和脚"。每个工具都是一个可调用的函数，Agent 根据当前状态选择合适的工具来执行。工具的设计需要遵循单一职责原则：每个工具只做一件事，但要把这件事做好。这样 Agent 才能灵活组合多个工具来完成复杂任务。

07_advanced_rag/02_agentic_rag/agentic_rag.py
# 工具定义：每个工具是一个独立的函数
def vector_search(query: str) -> str:
    """向量检索工具"""
    return f"[检索结果] 找到与'{query}'相关的文档片段。"

def rerank(query: str) -> str:
    """重排序工具"""
    return f"[重排序结果] Top-3 相关性分数为 0.95, 0.88, 0.82。"

def verify(query: str) -> str:
    """验证工具"""
    return f"[验证结果] 当前检索结果足以回答'{query}'。"

def generate(query: str) -> str:
    """生成工具"""
    return f"[生成结果] 基于检索和验证，生成最终回答。"
  • 复杂问答：当答案需要综合多个信息源、进行多步推理时，Agentic RAG 能够自主规划检索路径
  • 动态策略选择：当系统需要支持多种检索策略，且问题类型多样时，路由 Agent 能自动选择最优策略
  • 交互式检索：当用户问题模糊或不完整时，Agent 可以主动提问澄清，而不是盲目检索
  • 工具调用：当检索需要结合外部工具（如计算器、API 调用、数据库查询）时，Agent 能够协调多个工具
⚠️ 成本与延迟

Agentic RAG 需要多次 LLM 调用来完成 Thought-Action-Observation 循环，这显著增加了延迟和成本。在实际应用中，需要设置最大步数限制（通常 3-5 步），并监控 Token 消耗。对于简单问题，建议直接使用传统 RAG，避免不必要的 Agent 开销。

六、小结

Agentic RAG 将 Agent 技术引入 RAG 系统，实现了从"被动执行"向"主动决策"的转变。ReAct Agent 通过 Thought-Action-Observation 循环实现多步推理，路由 Agent 根据问题类型自动选择最佳检索策略。

Agentic RAG 的核心优势在于自主决策和多步推理能力，适合复杂问答和动态策略选择场景。但其成本较高，需要多次 LLM 调用，在实际应用中需要权衡收益和开销。建议在简单场景中使用传统 RAG，在复杂场景中使用 Agentic RAG，根据实际需求灵活选择。

在实际项目中，建议先用传统 RAG 快速上线，再根据用户反馈和业务复杂度逐步引入 Agentic RAG。可以从简单的路由 Agent 开始，根据问题类型选择不同的检索策略，再逐步升级到完整的 ReAct Agent 实现多步推理。这种渐进式的引入方式能够在控制成本的同时，逐步提升系统的智能化水平。
