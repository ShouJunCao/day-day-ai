7.5 权限控制与多租户 RAG

模块七：高级 RAG 技术 预计学习：50 分钟

学习目标

  • 理解 RAG 系统中权限控制的必要性和挑战
  • 掌握基于角色的访问控制（RBAC）模型
  • 学会多租户隔离的实现方案
  • 能够构建安全的 RAG 查询管道

一、为什么需要权限控制？

在企业级 RAG 应用中，不同用户对知识库的访问权限是不同的。高管可能有权访问所有文档，普通员工只能访问公开文档，特定项目的成员只能访问项目相关文档。如果 RAG 系统没有权限控制，用户可能通过检索获取到无权访问的敏感信息，造成严重的数据泄露风险。

权限控制的核心挑战在于：向量检索是基于语义相似度的，系统需要同时考虑"文档内容是否相关"和"用户是否有权访问该文档"两个维度。传统的数据库权限控制（如行级过滤）可以直接应用于向量检索，但实现方式有所不同。在向量数据库中，需要在检索阶段就加入权限过滤条件，而不是在检索后再过滤结果，这样既能保证安全性，又能提高效率。

此外，多租户场景下还需要确保租户间的数据完全隔离。租户 A 的用户不应该能检索到租户 B 的文档，即使在同一个向量索引中存储。这需要设计合理的隔离策略和过滤机制，确保数据不会跨租户泄露。在实际应用中，企业需要同时满足内部权限控制和多租户隔离的双重需求。

在实际应用中，权限控制不仅是技术问题，更是合规要求。许多行业（如金融、医疗、政务）都有严格的数据访问合规要求，RAG 系统必须满足这些要求才能被企业采用。因此，权限控制是 RAG 系统从实验走向生产的关键一步。

二、基于角色的访问控制（RBAC）

RBAC（Role-Based Access Control）是最常用的权限模型。它将权限分配给角色，然后将角色分配给用户。这样，用户的权限由其所拥有的角色决定，而不是直接分配给用户。这种间接映射的方式使得权限管理更加灵活和可扩展。

在 RAG 系统中，常见的角色包括：

  • Admin（管理员）：拥有所有权限，可以管理租户、用户、文档和权限配置
  • Editor（编辑者）：可以读取和写入文档，但不能删除或管理权限
  • Viewer（查看者）：只能读取文档，不能修改或删除

RBAC 的优势在于权限管理的集中化和标准化。当需要修改某个角色的权限时，只需要修改角色的权限配置，所有拥有该角色的用户会自动继承新的权限。这种方式大大减少了权限管理的复杂度，特别是在用户数量庞大的场景下。同时，RBAC 模型也便于审计和合规检查，因为权限变更都有明确的记录。

class PermissionManager:
    """
    权限管理器：基于角色的访问控制（RBAC）。

    权限模型：
    - Admin: 所有权限（读写删除管理）
    - Editor: 读写权限
    - Viewer: 只读权限
    """

    ROLE_PERMISSIONS = {
        Role.ADMIN: {Permission.READ, Permission.WRITE,
                     Permission.DELETE, Permission.ADMIN},
        Role.EDITOR: {Permission.READ, Permission.WRITE},
        Role.VIEWER: {Permission.READ},
    }

    def has_permission(self, user: User, permission: Permission) -> bool:
        """检查用户是否有指定权限"""
        return permission in self.ROLE_PERMISSIONS.get(user.role, set())

三、文档级权限

除了角色权限，文档本身也有访问级别。不同的文档有不同的敏感程度，需要设置不同的访问控制策略。

访问级别说明谁可以访问
Public（公开）所有人都可以访问同租户的所有用户
Internal（内部）内部文档有读取权限的用户
Restricted（受限）受限文档白名单中的用户
Confidential（机密）最高机密仅文档所有者

四、多租户隔离

多租户隔离是确保不同租户的数据不会互相访问的关键机制。在向量检索场景中，最常见的做法是在向量索引中加入租户 ID 作为命名空间，检索时自动过滤。这种命名空间隔离方案在性能和安全性之间取得了良好的平衡。

在实现层面，多租户隔离可以分为三个层次：存储层隔离、索引层隔离和查询层隔离。存储层隔离确保不同租户的文档存储在不同的物理或逻辑存储中；索引层隔离确保每个租户的向量索引是独立的；查询层隔离确保检索结果只包含当前租户有权访问的文档。这三个层次共同构成了完整的多租户隔离体系。

4.1 隔离方案对比

不同的业务场景需要不同的隔离方案。独立实例方案为每个租户提供完全独立的 RAG 系统实例，隔离级别最高但成本也最高；命名空间隔离在同一个向量索引中使用不同的命名空间来区分租户，成本适中；行级过滤则在检索时动态添加租户过滤条件，成本最低但实现最复杂。

方案隔离级别成本适用场景
独立实例物理隔离高高安全要求（金融/医疗）
命名空间隔离逻辑隔离中SaaS 多租户
行级过滤权限控制低内部多部门

五、安全 RAG 查询管道

安全 RAG 查询管道将权限检查和向量检索集成在一起，确保每次查询都经过权限验证。整个流程分为五个步骤：身份验证、租户隔离、向量检索、权限过滤、结果生成。每一步都有明确的安全检查点，确保数据不会泄露给无权访问的用户。

身份验证是第一步，系统需要确认用户的身份和所属租户。这一步通常通过 OAuth 或 JWT 等认证协议完成。租户隔离确定了用户的查询范围，确保用户只能检索到自己租户内的文档。向量检索在限定的租户范围内执行，避免了跨租户的数据泄露。权限过滤对检索结果进行二次检查，确保用户只能看到有权访问的文档。最后，结果生成将过滤后的文档内容构建为 Prompt 并发送给 LLM。

5.1 代码实现

class SecureRAGPipeline:
    """安全 RAG 管道：集成权限控制和多租户隔离"""

    def query(self, user: User, question: str, top_k: int = 5) -> dict:
        """安全查询：集成权限检查的 RAG 查询"""
        # 1. 在用户租户内检索
        raw_results = self.index.search(
            user.tenant_id, question, top_k * 2
        )

        # 2. 权限过滤
        filtered_results = []
        for result in raw_results:
            doc = self.documents.get(result["doc_id"])
            if doc and self.permission_mgr.can_access_doc(user, doc):
                filtered_results.append(result)
            if len(filtered_results) >= top_k:
                break

        # 3. 构建上下文并生成回答
        context = "\n\n".join(r["chunk"] for r in filtered_results)
        return {"results": filtered_results, "context": context}

六、小结

权限控制和多租户隔离是企业级 RAG 系统的必备能力。通过 RBAC 模型管理用户角色和权限，通过文档访问级别控制敏感内容的访问范围，通过多租户索引确保租户间数据隔离。这三层防护机制共同构成了完整的安全体系，确保 RAG 系统能够满足企业级的安全合规要求。

安全 RAG 查询管道将权限检查集成到检索流程中，确保每次查询都经过身份验证、租户隔离、权限过滤等多层安全检查。这种设计既保证了系统的安全性，又不影响检索效率。在实际应用中，建议在检索阶段就加入权限过滤条件，而不是在检索后再过滤结果，这样既能保证安全性，又能减少不必要的计算开销。

在实际项目中，建议根据业务需求选择合适的隔离方案：高安全要求的场景使用独立实例，SaaS 场景使用命名空间隔离，内部多部门使用行级过滤。同时，定期进行安全审计和权限审查，确保权限配置始终符合业务要求。权限管理不是一次性工作，而是需要持续维护和改进的过程。只有将安全意识融入到系统的每一个环节，才能真正实现企业级的数据安全。
