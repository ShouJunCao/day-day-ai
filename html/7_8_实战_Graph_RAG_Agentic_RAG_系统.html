一、为什么需要综合架构？

在前面的章节中，我们分别学习了 Graph RAG 和 Agentic RAG 的核心原理。Graph RAG 擅长处理实体关系和全局理解，而 Agentic RAG 擅长动态决策和多步推理。但在真实的企业场景中，单一技术往往难以满足所有复杂需求。企业知识库中的查询类型多样，从简单的事实查询到复杂的关系分析，从操作指南到数据对比，需要系统具备灵活的应对能力。

在实际的企业应用场景中，用户的查询往往跨越多种类型。例如，在金融领域，分析师不仅需要查询某家公司的基本资料（事实型问题），还需要分析该公司与供应链上下游企业的关联关系（关系型问题），甚至需要对比两家竞争对手的财务报表（比较型问题）。传统的纯向量检索 RAG 只能提供文本片段，难以处理复杂的实体关联；而纯图谱检索又无法覆盖非结构化的长文本细节。因此，我们需要一种能够将两者优势结合的架构，根据问题类型动态切换或组合不同的检索策略。

综合架构通过 Agent 路由模块识别问题类型，然后动态选择向量检索、图谱检索或混合检索，最后将结果融合并生成回答。这种设计兼顾了灵活性和准确性，能够应对企业知识库中多样化、深层次的查询需求。同时，结合前面学习的 CRAG 和 Self-RAG 技术，我们还可以在检索和生成阶段分别加入自我纠正机制，进一步提升系统的可靠性。

二、知识图谱构建模块

知识图谱是 Graph RAG 的核心。在本实战中，我们使用邻接表存储实体关系，支持快速遍历和路径查找。图谱的构建通常分为两步：实体抽取和关系识别。在实际生产环境中，这一步通常由 LLM 或专门的 NER（命名实体识别）/RE（关系抽取）模型完成。

在我们的简化实现中，实体包含唯一标识符、名称、类型和描述等属性。关系则记录源实体、目标实体、关系类型和权重。图的遍历使用广度优先搜索（BFS）算法，能够在最大深度限制内查找两个实体之间的所有路径，这对于理解概念之间的关联非常有帮助。

知识图谱的价值在于它能够将碎片化的文档信息组织成结构化的关系网络。例如，当用户询问"BERT 和 GPT 有什么关系"时，传统 RAG 可能只能找到分别提到两者的文档片段，而 Graph RAG 可以通过图谱遍历发现它们都基于 Transformer 架构，都使用自注意力机制等深层关联。这种基于关系的回答比简单的文本片段拼接更加深入和有洞察力。

class KnowledgeGraph:
    """知识图谱：存储实体和关系，支持图谱遍历"""

    def add_entity(self, entity: Entity):
        """添加实体到图谱"""
        self.entities[entity.entity_id] = entity
        if entity.entity_id not in self.adjacency:
            self.adjacency[entity.entity_id] = []

    def add_relation(self, relation: Relation):
        """添加双向关系"""
        self.relations.append(relation)
        self.adjacency[relation.source].append(relation.target)
        self.adjacency[relation.target].append(relation.source)

    def find_path(self, source: str, target: str, max_depth: int = 3):
        """BFS 查找实体间路径"""
        queue = [[source]]
        visited = {source}
        while queue:
            path = queue.pop(0)
            if path[-1] == target: return path
            for neighbor in self.adjacency.get(path[-1], []):
                if neighbor not in visited:
                    visited.add(neighbor)
                    queue.append(path + [neighbor])
        return []

三、Agent 路由模块

Agent 路由模块负责识别用户问题的意图类型，并动态选择最合适的检索策略。在本实战中，我们实现了四种问题类型：事实型（Factual）、比较型（Comparative）、关系型（Relational）和过程型（Procedural）。每种类型对应不同的检索管道，确保系统能够以最合适的方式回答用户的问题。

事实型问题通常涉及具体概念的定义或特征，适合使用向量检索快速匹配相关文本片段；比较型问题需要同时获取多个实体的信息并进行对比，适合混合检索结合向量和图谱的结果；关系型问题关注实体之间的关联，图谱检索能够提供结构化的关系路径；过程型问题关注操作步骤或方法，文档检索能够提供详细的流程说明。

在实际生产环境中，分类器可以基于更复杂的模型（如微调的分类模型或 LLM）来提高准确率。本实战中的基于关键词的分类是一个简化版本，但其核心思想——根据问题类型选择不同的检索策略——是通用的，可以应用于更复杂的分类器之上。

class AgentRouter:
    """Agent 路由器：根据问题类型选择最佳检索策略"""

    def route(self, query: str) -> str:
        query_type = self.classify_query(query)
        handler = self.routes.get(query_type, self._route_procedural)
        return handler(query, query_type)

    def classify_query(self, query: str) -> str:
        if any(kw in query for kw in ["什么", "谁", "哪里"]):
            return "factual"
        elif any(kw in query for kw in ["比较", "区别"]):
            return "comparative"
        elif any(kw in query for kw in ["关系", "关联"]):
            return "relational"
        return "procedural"

四、多源检索与融合

多源检索是综合架构的关键环节。系统同时执行向量检索和图谱检索，然后将结果合并去重，按置信度排序。向量检索擅长语义匹配，图谱检索擅长关系推理，两者互补能够显著提升召回质量。

完成系统构建后，我们通过不同类型的查询测试系统的表现。测试涵盖事实型问题（什么是 Transformer）、比较型问题（BERT 和 GPT 的区别）、关系型问题（Transformer 与自注意力的关系）。系统能够正确路由问题，选择合适的检索策略，并返回高质量的回答。

五、小结

本实战项目将 Graph RAG 的知识表示能力与 Agentic RAG 的动态决策能力有机结合，构建了一个完整的企业级 RAG 系统。通过知识图谱构建、Agent 智能路由、多源检索融合等核心模块，系统能够灵活应对不同类型的复杂查询。

在实际生产环境中，建议根据业务数据规模逐步迭代：初期使用向量检索验证核心需求，中期引入知识图谱增强关系推理能力，后期加入 Agent 路由和自我纠正机制提升系统智能化水平。同时，配合 7.4 节的增量更新机制和 7.5 节的权限控制，即可构建出安全、高效、可扩展的企业级知识库问答系统。

在整个系统的设计过程中，还需要考虑性能优化、缓存策略、错误处理等非功能性需求。例如，对于高频查询可以使用缓存机制减少重复计算，对于图谱遍历可以设置最大深度限制避免过度搜索。这些工程实践细节在实际落地时同样重要，需要在架构设计阶段就充分考虑。此外，系统监控和日志记录也是必不可少的，它们能够帮助运维团队及时发现和解决问题，确保系统的稳定运行。
