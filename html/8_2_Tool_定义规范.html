一、JSON Schema 在工具定义中的作用

在 Function Calling 中，JSON Schema 是描述工具接口格式的标准方式。它定义了工具的名称、功能描述和参数结构，是 LLM 理解如何调用工具的关键。一个规范的 JSON Schema 定义应该包含工具名称、功能描述、参数类型、参数描述、必填项等信息。

JSON Schema 的核心价值在于提供了一种结构化的方式来描述工具的输入格式。通过这种结构化的描述，LLM 能够准确地理解每个参数的含义、类型和约束条件，从而生成正确的工具调用请求。如果没有 JSON Schema，LLM 只能通过自然语言描述来理解工具接口，这容易导致参数类型错误或遗漏必填参数等问题。

在实际应用中，OpenAI、Anthropic 等主流 LLM 提供商都使用 JSON Schema 作为工具定义的标准格式。虽然具体实现细节可能有所不同，但核心结构基本一致：一个包含 type、function.name、function.description、function.parameters 的嵌套对象。

二、参数类型与约束

JSON Schema 支持多种数据类型：string（字符串）、integer（整数）、number（数字）、boolean（布尔值）、array（数组）、object（对象）。在工具定义中，正确选择参数类型至关重要，因为它直接影响 LLM 生成的参数值格式。

除了基本类型，JSON Schema 还提供了丰富的约束机制：enum（枚举）限制参数只能从预定义的值中选择；required（必填）指定哪些参数是必需的；default（默认值）为可选参数提供默认值；minimum/maximum（最小/最大值）限制数值范围；pattern（正则表达式）限制字符串格式。

合理使用这些约束能够显著提高 LLM 的工具调用准确率。例如，对于性别参数，使用 enum 约束 ["male", "female", "other"] 比使用 string 类型更好，因为 LLM 不会生成无效的值。对于可选参数，提供默认值可以减少 LLM 生成不完整参数组合的可能性。

约束类型作用示例推荐场景
enum限制可选值["low", "medium", "high"]枚举型参数（优先级、状态等）
required标记必填项["city"]不可缺少的核心参数
default设置默认值"celsius"有合理默认值的可选参数
minimum/max数值范围限制minimum: 1, maximum: 100数量、分数等数值参数
pattern字符串格式校验"^[0-9]{11}$"手机号、邮箱等格式要求
minItems/maxItems数组长度限制minItems: 1, maxItems: 10列表型参数

三、高质量参数描述编写

参数描述是工具定义中最容易被忽视但最重要的部分。一个好的参数描述应该包含三要素：参数含义（这个参数代表什么）、格式要求（参数应该是什么格式）、示例值（举一个具体的例子）。这样的描述能够帮助 LLM 准确理解参数的用途和格式要求，从而生成正确的参数值。

参数描述的常见问题包括：过于简短（如只写"城市名称"而不说明格式要求）、缺少示例（LLM 不知道该用什么格式）、术语不一致（与工具其他部分的术语不匹配）、使用歧义词汇（如"时间"没有说明格式是"2024-01-15"还是"2024/01/15"还是时间戳）。这些问题会导致 LLM 生成不正确的参数值，从而影响工具调用的成功率。

在实际项目中，建议为每个工具定义建立参数描述模板，确保所有参数描述都遵循统一的格式和风格。对于复杂参数，可以在描述中包含格式示例和常见错误提示，帮助 LLM 更好地理解和生成正确的参数值。例如，对于日期参数，应该明确说明格式是"YYYY-MM-DD"并给出具体示例"2024-01-15"，避免 LLM 生成"2024年1月15日"或"01/15/2024"等不一致的格式。

3.2 工具定义构建器

为了简化工具定义的创建过程，我们可以实现一个构建器模式，通过链式调用来逐步构建完整的工具定义。这种方式比手动编写 JSON 更直观，也更容易保证定义的规范性。

08_function_calling/02_tool_definition_spec/tool_definition_spec.py
class ToolSchemaBuilder:
    """
    工具 Schema 构建器：通过链式调用构建工具定义。
    """

    def __init__(self, name: str, description: str):
        self.schema = ToolSchema(name=name, description=description)

    def add_param(self, name: str, type: str, description: str,
                  required: bool = False, enum: List[str] = None,
                  default: Any = None) -> 'ToolSchemaBuilder':
        """添加参数"""
        self.schema.parameters.append(ParamDef(
            name=name, type=type, description=description,
            required=required, enum=enum, default=default,
        ))
        return self

    def build(self) -> ToolSchema:
        """构建并返回 Schema"""
        return self.schema


# 使用示例
tool = ToolSchemaBuilder("send_email", "发送邮件到指定收件人") \
    .add_param("to", "string", "收件人邮箱地址", required=True) \
    .add_param("subject", "string", "邮件主题", required=True) \
    .add_param("body", "string", "邮件正文内容", required=True) \
    .add_param("priority", "string", "优先级", required=False,
               enum=["low", "normal", "high"], default="normal") \
    .build()

四、Schema 验证

在将工具定义发送给 LLM 之前，对其进行验证是一个好习惯。验证可以确保工具名称符合命名规范、描述不为空、参数类型有效、没有重复参数等。通过验证，我们可以在早期发现并修复定义错误，避免 LLM 因为不规范的定义而产生误解。

验证器应该检查以下方面：工具名称是否以字母或下划线开头且只包含字母数字下划线；工具描述是否为空或过长；参数数量是否合理（建议不超过 20 个）；每个参数的类型是否在支持的类型集合中；参数描述是否为空；参数名称是否有重复。

4.1 验证器实现

08_function_calling/02_tool_definition_spec/tool_definition_spec.py
class SchemaValidator:
    """工具定义验证器：检查工具定义是否符合规范"""

    VALID_TYPES = {"string", "integer", "number", "boolean", "array", "object"}
    MAX_DESCRIPTION_LENGTH = 200
    MAX_PARAMS = 20

    def validate(self, schema: ToolSchema) -> List[str]:
        """验证工具定义，返回错误列表"""
        errors = []

        # 1. 名称检查
        if not schema.name:
            errors.append("工具名称不能为空")
        if not re.match(r'^[a-zA-Z_][a-zA-Z0-9_]*$', schema.name):
            errors.append(f"工具名称 '{schema.name}' 不符合命名规范")

        # 2. 描述检查
        if not schema.description:
            errors.append(f"工具 '{schema.name}' 缺少描述")
        elif len(schema.description) > self.MAX_DESCRIPTION_LENGTH:
            errors.append(f"工具描述过长（>{self.MAX_DESCRIPTION_LENGTH}字）")

        # 3. 参数检查
        seen_names = set()
        for p in schema.parameters:
            if p.name in seen_names:
                errors.append(f"参数 '{p.name}' 重复定义")
            seen_names.add(p.name)
            if p.type not in self.VALID_TYPES:
                errors.append(f"参数 '{p.name}' 类型 '{p.type}' 无效")
            if not p.description:
                errors.append(f"参数 '{p.name}' 缺少描述")

        return errors

五、最佳实践总结

编写高质量的工具定义是 Function Calling 成功的关键。以下是经过实践验证的最佳实践：工具名称应该使用动词加名词的格式（如 get_weather、search_knowledge），使 LLM 能够直观理解工具的功能；工具描述应该简洁明了地说明工具的功能和使用场景，避免过于冗长；参数描述应该包含含义、格式要求和示例值，确保 LLM 能够准确理解。

在约束使用方面，对于有限选项的参数一定要使用 enum 约束，避免 LLM 生成无效值；必填参数必须明确标记为 required，避免 LLM 遗漏关键参数；对于有合理默认值的可选参数，提供 default 值可以减少 LLM 的决策负担。此外，建议在开发过程中使用验证器对所有工具定义进行检查，确保定义质量。

对于复杂参数类型，如 array 和 object，建议在参数描述中提供具体的 JSON 示例。例如，对于 tags 参数（array 类型），描述可以是"标签列表，如 ['AI', 'RAG', 'LLM']，每个标签不超过 20 个字符"。对于配置参数（object 类型），描述可以是"配置对象，如 {'timeout': 30, 'retry': 3}，timeout 为超时秒数，retry 为重试次数"。

工具描述简洁说明功能和使用场景LLM 准确判断调用时机
参数描述含义 + 格式 + 示例LLM 生成正确参数值
枚举约束有限选项使用 enum避免无效参数值
必填标记核心参数标记 required避免遗漏关键参数
验证器开发中使用验证器检查早期发现定义错误
💡 实战建议

在实际项目中，建议为每个工具定义建立模板和验证流程。可以先使用 ToolSchemaBuilder 构建工具定义，然后通过 SchemaValidator 验证，最后转换为 OpenAI 格式发送给 LLM。这种标准化的流程能够确保工具定义的质量一致性，减少因定义错误导致的工具调用失败。

六、小结

Tool 定义规范是 Function Calling 的核心基础。通过 JSON Schema 描述工具的接口格式，通过高质量的参数描述帮助 LLM 理解工具的使用方式，通过约束机制确保参数值的正确性。掌握这些规范对于构建可靠的 Function Calling 系统至关重要。

在实际项目中，建议将工具定义管理纳入开发流程的规范化管理中。每次新增工具时，都应该使用构建器创建、验证器检查、标准化输出，确保工具定义的质量一致性。这种工程化的方法能够显著减少因定义错误导致的工具调用失败。
