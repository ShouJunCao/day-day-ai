8.4 工具调用的错误处理、重试与超时

模块八：Function Calling 预计学习：50 分钟

学习目标

  • 掌握工具调用失败的四种处理策略
  • 理解指数退避重试算法的原理和实现
  • 学会实现降级方案和超时检测
  • 能够设计完整的错误处理流程

一、为什么需要错误处理？

在 Function Calling 中，工具调用可能因为多种原因失败：网络超时、API 限流、服务宕机、参数错误、权限不足等。如果没有完善的错误处理机制，一次简单的工具调用失败就可能导致整个任务中断，严重影响用户体验和系统可靠性。在实际生产环境中，工具调用的失败率通常在 1%~5% 之间，对于依赖多个工具调用的复杂任务，整体失败率会显著增加。

错误处理的核心目标是在工具调用失败时，尽可能优雅地恢复或降级，而不是直接抛出异常。我们定义了四种基本的错误处理策略：重试（Retry）在临时性故障时自动重新尝试，降级（Fallback）在主服务不可用时切换到备用方案，跳过（Skip）在非关键步骤失败时继续执行后续步骤，中止（Abort）在致命错误时立即停止整个流程。

选择合适的错误处理策略取决于错误的类型和业务场景。对于临时性的网络故障，重试是最有效的策略；对于服务宕机或 API 变更，降级方案能够保证系统的基本功能；对于非关键的数据补充步骤，跳过策略可以避免阻塞主流程；对于数据一致性要求极高的操作，中止策略能够防止产生不一致的状态。在实际项目中，通常会组合使用多种策略，形成多层次的错误处理机制，确保系统在各种异常情况下都能保持基本的可用性。

二、重试机制

重试是最常用的错误处理策略，适用于临时性故障（如网络抖动、服务短暂不可用、API 限流等）。但简单的立即重试可能加剧问题，因此我们采用指数退避算法（Exponential Backoff）结合随机抖动（Jitter）来实现智能重试。

指数退避的核心思想是：每次重试的等待时间按指数增长。第一次重试等待 1 秒，第二次等待 2 秒，第三次等待 4 秒，依此类推。这样可以避免在服务恢复期间产生大量请求风暴。随机抖动则在指数退避的基础上添加一个随机因子，避免多个客户端同时重试导致的同步问题。这种组合策略被广泛应用于分布式系统的重试机制中，是业界公认的最佳实践。

重试策略的关键参数包括：最大重试次数（避免无限重试）、基础等待时间、最大等待时间上限、指数底数、是否启用抖动。这些参数需要根据具体的业务场景和 API 特性进行调整，在重试成功率和响应延迟之间找到平衡点。一般来说，对于非关键的辅助工具，最大重试次数设置为 2~3 次即可；对于关键的核心工具，可以设置到 5 次以上。基础等待时间通常设置为 1 秒左右，最大等待时间上限建议不超过 30 秒，避免用户等待时间过长。

def _wait_before_retry(self, attempt: int):
    """计算重试等待时间（指数退避 + 抖动）"""
    delay = self.retry_config.base_delay * (
        self.retry_config.exponential_base ** attempt
    )
    delay = min(delay, self.retry_config.max_delay)

    if self.retry_config.jitter:
        delay *= (0.5 + random.random() * 0.5)

三、降级方案

降级（Fallback）是当主服务不可用时的备用方案。与重试不同，降级不是等待主服务恢复，而是切换到另一个可用的替代方案。降级的核心价值在于保证系统的可用性——即使主服务完全宕机，系统仍然能够提供基本功能。

降级的实现方式有多种：使用缓存数据替代实时查询，使用简化的本地算法替代复杂的远程服务，使用备用的 API 供应商替代主供应商。在实际项目中，降级方案通常是经过充分测试和验证的，确保在主服务不可用时能够提供可接受的服务质量。

注册降级方案的最佳实践是：为每个关键工具定义一个降级函数，当工具调用失败且重试耗尽后自动切换到降级函数。降级函数的签名应该与原始工具一致，确保调用方无需修改代码。同时，系统应该记录降级事件，便于后续分析和改进。

3.1 核心实现

注册降级方案的最佳实践是：为每个关键工具定义一个降级函数，当工具调用失败且重试耗尽后自动切换到降级函数。降级函数的签名应该与原始工具一致，确保调用方无需修改代码。同时，系统应该记录降级事件，便于后续分析和改进。

08_function_calling/04_error_handling/error_handling.py
class ErrorHandler:
    def register_fallback(self, tool_name: str, fallback_func: Callable):
        """注册降级函数"""
        self.fallbacks[tool_name] = fallback_func

    def call_with_handling(self, tool_name, arguments):
        # ... 重试逻辑 ...
        # 重试耗尽后尝试降级
        if tool_name in self.fallbacks:
            try:
                fallback_result = self.fallbacks[tool_name](**arguments)
                result.result = str(fallback_result)
                result.used_fallback = True
                result.success = True
            except Exception as e:
                result.error += f"，降级也失败: {e}"
        return result

四、超时检测

超时检测是防止工具调用无限等待的关键机制。当一个工具调用超过预设的时间限制时，系统应该主动中断该调用，而不是无限制地等待。超时检测不仅可以提高系统的响应速度，还可以防止资源泄漏和级联故障。

超时时间的设定需要根据工具的特性来调整：对于本地计算工具，超时时间可以设置得较短（如 5 秒）；对于网络请求工具，超时时间需要设置得较长（如 30 秒）；对于可能耗时较长的工具（如大文件处理），超时时间可能需要设置到数分钟。合理的超时时间应该在保证大多数正常调用能够完成的前提下，尽可能减少异常调用对系统的影响。

在实际实现中，超时检测可以使用线程超时、异步 IO 超时或进程超时等方式。在我们的简化实现中，通过 try-except 捕获超时异常并标记结果。在生产环境中，建议使用 asyncio.wait_for 或 concurrent.futures 来实现精确的超时控制。超时后系统可以选择重试、降级或直接返回错误，具体取决于业务需求和工具的重要性。

五、错误日志与监控

错误日志是错误处理系统中不可或缺的一部分。每次工具调用失败时，系统应该记录详细的错误信息，包括工具名称、调用参数、错误类型、错误消息、时间戳等。这些信息对于问题排查和系统优化至关重要。通过分析错误日志，我们可以发现潜在的共性问题，例如某个工具在特定时间段频繁超时，或者某个参数的错误率明显高于其他参数。

5.1 错误统计实现

08_function_calling/04_error_handling/error_handling.py
def _log_error(self, tool_name: str, arguments: Dict, error: str):
    """记录错误日志"""
    self.error_log.append({
        "tool": tool_name,
        "arguments": arguments,
        "error": error,
        "timestamp": time.time(),
    })

def get_error_stats(self) -> Dict[str, Any]:
    """获取错误统计"""
    return {
        "total_errors": len(self.error_log),
        "recent_errors": self.error_log[-5:],
    }

错误统计可以帮助我们发现潜在的系统问题：如果某个工具的错误率持续上升，可能意味着该服务正在出现问题；如果超时错误占比很高，可能需要调整超时时间或优化服务性能；如果某个参数的错误率特别高，可能意味着参数验证逻辑需要加强。通过持续监控和分析错误数据，我们可以不断优化错误处理策略，提高系统的整体可靠性。

六、小结

工具调用的错误处理、重试与超时是构建可靠 Function Calling 系统的关键环节。通过指数退避重试算法，我们可以在临时性故障时自动恢复；通过降级方案，我们可以在主服务不可用时保持系统可用；通过超时检测，我们可以防止无限等待导致的资源浪费；通过错误日志和监控，我们可以持续优化系统的可靠性。这四个组件共同构成了一个完整的错误处理体系，缺一不可。

在实际项目中，建议为每个工具调用都配置完整的错误处理流程：首先设置合理的超时时间，然后配置指数退避重试策略，接着注册降级方案作为最后保障，最后确保所有错误都被记录和分析。同时，错误处理策略的选择应该根据工具的重要性和业务场景来决定，不能一概而论。对于关键路径上的工具调用，应该采用更积极的重试和降级策略；对于非关键的辅助工具，可以采用简单的跳过策略以避免阻塞主流程。在生产环境中，还应该配合监控告警系统，当错误率超过阈值时及时通知运维团队进行干预。
