9.1 MCP 协议概述与设计理念

模块九：MCP 协议 预计学习：50 分钟

学习目标

  • 理解 MCP 协议的核心概念和设计动机
  • 掌握 MCP 协议的三层架构（Transport / Protocol / Capabilities）
  • 了解 MCP 的生命周期（Initialize → 能力协商 → 交互 → 关闭）
  • 掌握 JSON-RPC 2.0 消息格式和三大能力（Tools / Resources / Prompts）

一、什么是 MCP 协议？

MCP（Model Context Protocol）是 Anthropic 于 2024 年 11 月提出的开放协议，旨在标准化 AI 应用与外部数据源和工具的集成方式。在 MCP 出现之前，每个 AI 应用都需要为不同的数据源和工具编写专用的集成代码，导致大量的重复工作和集成成本。MCP 通过统一的协议层，解决了 AI 应用与外部系统之间的"最后一公里"连接问题。

MCP 的核心设计理念是：用统一的协议替代点对点的集成。就像 USB-C 接口统一了各种设备的物理连接方式一样，MCP 试图统一 AI 应用与外部系统之间的软件连接方式。通过 MCP，开发者只需要编写一次 MCP 服务器（暴露数据源或工具），就可以被任何支持 MCP 的 AI 客户端使用，无需为每个 AI 应用单独编写集成代码。

MCP 协议基于 JSON-RPC 2.0，支持三种传输层：stdio（标准输入输出，适合本地进程间通信）、SSE（Server-Sent Events，适合远程通信）和 HTTP（适合 Web 服务）。协议定义了三种核心能力：Tools（工具调用）、Resources（资源读取）和 Prompts（模板提示词），涵盖了 AI 应用与外部系统交互的主要场景。

二、为什么需要 MCP 协议？

在 MCP 出现之前，AI 应用与外部系统的集成存在严重的碎片化问题。每个 AI 应用（如 Claude、ChatGPT、Cursor）都需要为每个数据源（如 GitHub、Google Drive、Slack）编写专用的集成代码。如果有 N 个 AI 应用和 M 个数据源，就需要编写 N×M 个集成适配器。这种点对点的集成模式导致了大量的重复工作、维护成本高、生态系统碎片化等问题。

MCP 通过引入统一的协议层，将集成复杂度从 N×M 降低到 N+M。每个数据源只需要实现一次 MCP 服务器，就可以被所有支持 MCP 的 AI 客户端使用。同样，每个 AI 客户端只需要实现一次 MCP 客户端，就可以连接所有 MCP 服务器。这种统一的方式大幅降低了集成成本，促进了生态系统的健康发展。

此外，MCP 协议的设计考虑了安全性、可扩展性和互操作性。它支持能力协商（客户端和服务器在初始化时交换各自支持的能力），支持订阅机制（客户端可以订阅资源变更通知），支持版本兼容性检查，确保不同版本的客户端和服务器能够正确协作。

三、MCP 协议生命周期

MCP 协议的生命周期包含四个阶段：初始化（Initialize）、能力协商、交互和关闭。在初始化阶段，客户端向服务器发送 initialize 请求，包含客户端信息和协议版本。服务器回复其能力（支持的 Tools、Resources、Prompts）和服务器信息。随后客户端发送 initialized 通知，确认握手完成。在能力协商阶段，客户端可以通过 tools/list、resources/list、prompts/list 等方法获取服务器提供的能力列表。在交互阶段，客户端可以调用工具（tools/call）、读取资源（resources/read）和获取 Prompt（prompts/get）。最后，在关闭阶段，任何一方都可以断开连接。

这种生命周期设计确保了客户端和服务器在开始正式交互之前，已经就协议版本和支持的能力达成了一致。能力协商机制使得不同版本的客户端和服务器可以互操作：即使客户端不支持某个能力，也不会影响其他能力的正常使用。

四、JSON-RPC 2.0 消息格式

MCP 协议基于 JSON-RPC 2.0，这是一种轻量级的远程过程调用协议。JSON-RPC 2.0 定义了三种消息类型：请求（Request）、响应（Response）和通知（Notification）。请求包含方法名和参数，期望收到响应；响应包含请求的结果或错误信息；通知是单向消息，不需要响应。

在 MCP 中，客户端通过发送请求来调用服务器的方法（如 initialize、tools/list、tools/call），服务器通过响应返回结果或错误。客户端还可以通过发送通知来告知服务器某些事件（如 initialized 通知）。JSON-RPC 2.0 的消息格式简洁明了，易于实现和调试，是 MCP 协议选择它作为底层协议的重要原因。

4.1 JSON-RPC 消息结构

JSON-RPC 2.0 定义了三种消息类型：请求（Request）包含方法名和参数，期望收到响应；响应（Response）包含请求的结果或错误信息；通知（Notification）是单向消息，不需要响应。在 MCP 中，客户端通过发送请求来调用服务器的方法，服务器通过响应返回结果或错误，客户端还可以通过发送通知来告知服务器某些事件。

请求消息

JSON-RPC 请求格式
{
    "jsonrpc": "2.0",
    "id": 1,
    "method": "initialize",
    "params": {
        "protocolVersion": "2024-11-05",
        "capabilities": {},
        "clientInfo": {"name": "demo-client", "version": "1.0.0"}
    }
}

响应和通知消息

JSON-RPC 响应与通知格式
// 响应消息（成功）
{
    "jsonrpc": "2.0",
    "id": 1,
    "result": {
        "protocolVersion": "2024-11-05",
        "capabilities": {"tools": {"listChanged": true}},
        "serverInfo": {"name": "demo-server", "version": "1.0.0"}
    }
}

// 响应消息（错误）
{
    "jsonrpc": "2.0",
    "id": 1,
    "error": {"code": -32601, "message": "Method not found"}
}

// 通知消息（不需要响应）
{"jsonrpc": "2.0", "method": "notifications/initialized"}

4.2 Python 实现示例

Python（MCP 消息构建）
class MCPMessage:
    """MCP JSON-RPC 消息"""
    def __init__(self, method=None, params=None, id=None):
        self.jsonrpc = "2.0"
        self.id = id
        self.method = method
        self.params = params

    def to_dict(self):
        data = {"jsonrpc": "2.0"}
        if self.id is not None:
            data["id"] = self.id
        if self.method:
            data["method"] = self.method
            if self.params:
                data["params"] = self.params
        return data

五、三大核心能力

MCP 协议定义了三种核心能力，分别对应 AI 应用与外部系统交互的三种主要场景。这三种能力通过统一的 JSON-RPC 2.0 协议暴露，客户端可以在能力协商阶段发现服务器支持哪些能力，然后在交互阶段按需调用。

Tools（工具调用）：允许 AI 客户端调用服务器提供的工具。每个工具包含名称、描述和输入参数 Schema。客户端通过 tools/list 获取可用工具列表，通过 tools/call 执行工具调用并获取结果。这是最常用的能力，对应 Function Calling 的场景。

Resources（资源读取）：允许 AI 客户端读取服务器提供的资源（如文件、数据库记录、API 数据等）。每个资源通过 URI 标识，客户端通过 resources/list 获取资源列表，通过 resources/read 读取资源内容。资源还支持订阅机制，当资源内容变更时，服务器可以主动通知客户端。

Prompts（Prompt 模板）：允许 AI 客户端获取服务器提供的可复用 Prompt 模板。每个 Prompt 包含名称、描述和参数列表。客户端通过 prompts/list 获取可用 Prompt 列表，通过 prompts/get 获取填充参数后的 Prompt 内容。这在需要标准化 AI 交互流程的场景中非常有用。

六、MCP 与 Function Calling 的关系

MCP 和 Function Calling 解决的是不同层面的问题。Function Calling 是 LLM 提供商（如 OpenAI、Anthropic）提供的一种能力，允许模型在生成回答时调用外部工具。它关注的是模型如何"知道"有哪些工具可用以及如何"决定"调用哪个工具。而 MCP 是一个更高层的协议，它关注的是如何标准化 AI 应用与外部系统之间的连接方式。

可以把 MCP 看作是 Function Calling 的"基础设施层"。Function Calling 定义了模型与工具之间的交互方式，但没有规定工具如何被发现、如何被注册、如何被管理。MCP 则提供了完整的工具生命周期管理：工具注册、发现、调用、结果返回。在实际应用中，MCP 服务器可以通过 MCP 协议暴露工具，AI 客户端通过 MCP 协议获取工具列表并调用，然后利用 Function Calling 能力让模型决定何时调用哪个工具。

💡 核心理解

MCP 是"连接协议"（如何连接 AI 与外部系统），Function Calling 是"调用机制"（模型如何决定调用哪个工具）。两者互补而非竞争。在实际项目中，MCP 负责暴露和管理工具，Function Calling 负责让模型智能地选择和使用这些工具。

七、小结

MCP（Model Context Protocol）是 Anthropic 提出的开放协议，通过统一的 JSON-RPC 2.0 协议层，解决了 AI 应用与外部系统之间的碎片化集成问题。它将集成复杂度从 N×M 降低到 N+M，促进了生态系统的健康发展。MCP 定义了三种核心能力：Tools（工具调用）、Resources（资源读取）和 Prompts（Prompt 模板），涵盖了 AI 应用与外部系统交互的主要场景。
